TittanWare: una plataforma, todos los procesos de la operación

TittanWare reúne en una sola aplicación web la logística, el transporte, el mantenimiento, la producción, la calidad, el talento humano y las finanzas de una empresa. Cada cliente contrata los módulos que necesita y trabaja sobre su propia base de datos aislada.

Python 3.12 · FastAPI · PostgreSQL 16 React 18 · TypeScript · Material UI Despliegue en Docker
20módulos contratables, más el núcleo de acceso
≈2.000operaciones en la API REST
273pantallas en el portal web
416tablas en el esquema de cada cliente
Plataforma

Arquitectura

Un frontend de una sola página habla con una API REST. La API guarda los datos de cada cliente en un esquema propio de PostgreSQL y las sesiones de usuario en Redis.

Plataforma

Aislamiento por cliente

Cada empresa cliente vive en su propio esquema de PostgreSQL, con su juego completo de tablas. Ninguna consulta de un módulo puede leer datos de otra empresa, porque desde su conexión esos datos no existen.

Al inicio de cada petición la API decide a qué cliente pertenece y fija el search_path de la conexión en el esquema de ese cliente. Desde ahí, el código de los módulos escribe consultas normales, sin filtros por empresa.

Por qué un esquema y no una columna

La alternativa habitual es agregar una columna tenant_id a cada tabla y filtrar por ella en cada consulta. Con más de 400 tablas y cerca de dos mil rutas, bastaría un WHERE olvidado para exponer datos de otra empresa. Con un esquema por cliente ese olvido no es posible.

De dónde sale el cliente

El cliente viaja dentro del token de acceso, firmado por el servidor. No se toma de una cabecera ni de la URL: si se pudiera cambiar sin invalidar la firma, un usuario válido de una empresa podría pedir datos de otra.

            return await call_next(request)

  • El esquema de un cliente se llama cli_<código>. El cliente que existía antes de la plataforma multicliente conserva el esquema public.
  • El código solo admite minúsculas, dígitos y guion bajo, empieza por letra y tiene como máximo 40 caracteres. Así no hay forma de inyectar SQL por el nombre del esquema, que debe interpolarse porque search_path no admite parámetros.
  • El esquema activo se guarda en una ContextVar: cada petición asíncrona tiene el suyo y se limpia al terminar.
  • Lo que es común a la plataforma vive en public: el registro de clientes, sus módulos contratados, los pagos y las sesiones del celular como escáner.
Consecuencias prácticas

Se puede respaldar, restaurar o mudar a un servidor distinto a una sola empresa sin tocar a las demás (pg_dump -n cli_<código>). Al dar de alta una empresa se crea su esquema y sus tablas en el momento.

Plataforma

Recorrido de una petición

Toda llamada a /api/v1 pasa por las mismas comprobaciones, en este orden. Las tres primeras son globales: una ruta nueva las recibe sin declararlas.

  1. nginx recibe la petición

    Termina el TLS, sirve los archivos del portal y reenvía a la API todo lo que empieza por /api. La base de datos y Redis no tienen puertos abiertos al exterior.

  2. Control de módulos contratados

    Se identifica el módulo por el prefijo de la ruta (gana el prefijo más largo) y se compara con lo que la empresa del token (cli) tiene contratado. Las rutas del núcleo de acceso siempre pasan.

    Si no está contratado: 403 «Su empresa no tiene contratado el módulo…». Funciona igual aunque alguien escriba la URL a mano.

  3. Resolución del cliente

    Se lee el esquema del token (esq), se valida y se fija para la conexión a la base de datos de esta petición.

  4. Sesión obligatoria

    Todas las rutas exigen token salvo una lista pública explícita. El token debe estar vigente y su sesión (sid) debe seguir viva en Redis.

    Sin token o con sesión cerrada: 401. Si Redis no responde: 503 «No se pudo validar la sesión».

  5. Permisos de la ruta

    Cada ruta declara lo que pide: usuario autenticado, un rol (supervisor, administrador), un permiso de pantalla del perfil, o un permiso de la consola del operador.

    Sin el permiso: 403 «Acceso denegado».

  6. Lógica de negocio

    El endpoint valida la entrada con Pydantic y delega en los motores de app/core lo que tiene reglas propias: contabilidad, inventario, planeación, facturación.

Qué lleva el token

ClaimContenido
subIdentificador del usuario.
cliCódigo de la empresa. Lo usa el control de módulos.
esqEsquema de la base de datos de la empresa. Lo usa la resolución del cliente.
usrNombre de usuario, para firmar registros sin consultar la base en cada petición.

depSolo en el portal del depositante: limita la API a su propio portal.

Reglas de la sesión

Vencimiento

La sesión se cierra tras 10 minutos sin actividad de la persona y dura como máximo 12 horas aunque se use sin parar.

Solo cuenta la actividad real: el navegador envía X-Inactividad con los segundos desde la última tecla, clic o toque. Las consultas automáticas de una pestaña abierta no la mantienen viva.

Cierre inmediato

Salir, cambiar la clave, que un administrador la restablezca o que desactive al usuario cierra la sesión en el acto, aunque el token no haya vencido.

Las contraseñas se guardan con Argon2id. Las anteriores en bcrypt se convierten solas en el siguiente ingreso.

Permisos en tres capas

Para que una persona use una pantalla, su empresa debe tener el módulo contratado y su perfil debe darle acceso. Las dos condiciones se comprueban en el servidor en cada petición.

La empresa

Módulos contratados

Qué partes de la plataforma puede usar la empresa. Se gestiona desde la consola del operador y tiene efecto inmediato.

ModulosMiddleware
La persona

Perfil y rol

Qué pantallas ve cada usuario dentro de su empresa. Un perfil solo puede abrir módulos que la empresa tenga contratados.

require_module_permission(…)
El operador

Administración de la plataforma

Dar de alta, editar o suspender empresas. Lo tiene solo la empresa marcada como operadora en el registro, fuera de cualquier esquema de cliente.

exigir("empresas.crear")
Por qué el operador se marca fuera del esquema

El rol ADMINISTRADOR existe dentro de cada empresa y administra solo esa empresa. Si la marca de operador viviera dentro del esquema de un cliente, ese cliente podría dársela a sí mismo y gestionar a los demás.

Lo que el portal oculta según los módulos contratados es comodidad de interfaz. La decisión real la toma siempre el servidor.

Funcionalidad

Motores de cálculo

Las reglas de negocio con fórmulas propias viven en app/core, separadas de los endpoints. Cada cálculo existe una sola vez y lo comparten las pantallas, los tableros y los informes, así que dos vistas del mismo dato no pueden dar cifras distintas.

ERP

Motor contable

Convierte cada hecho económico en un asiento de partida doble. Un asiento que no cuadra cancela la transacción completa: la factura no se guarda sin su contabilización.

core/erp_motor.py
ERP · POS

Facturación electrónica DIAN

Numera contra la resolución vigente con una operación atómica, sin pasar del rango autorizado. Calcula el CUFE / CUDE con SHA-384 según el anexo técnico.

NumFac + FecFac + HorFac + ValFac + 01 + ValIVA + … + NitOFE + NumAdq + ClaveTécnica + TipoAmbiente
core/facturacion_dian.py
APS

Planeación en cascada

De la demanda histórica al plan: pronóstico, inventario objetivo (stock de seguridad, punto de reorden, EOQ), DRP, MPS/MRP, carga de recursos (RCCP) y consolidación de traslados en camiones. Es una función pura de sus datos, así que se puede probar y simular escenarios.

core/aps/motor.py
Inventario

Kárdex con costo promedio ponderado

Mueve existencias y deja kárdex para el inventario y las órdenes de trabajo. Las salidas sin existencia se registran y quedan marcadas en lugar de bloquear la operación.

costo = (saldo × promedio + cantidad × costo_entrada) ÷ (saldo + cantidad)
core/inventario_kardex.py
WMS

Slotting y tareas dirigidas

Propone la ubicación de cada producto según su rotación ABC y el recorrido en serpentina por pasillos, con la zona dorada en los niveles 1 y 2. Al operario se le entrega la siguiente tarea por prioridad, cercanía y antigüedad.

core/wms_slotting.py · wms_tareas_dirigidas.py
WMS · 3PL

Liquidación del servicio logístico

Reconstruye día a día, desde el kárdex, las unidades, los m³, las posiciones y las estibas de cada depositante. Permite liquidar cualquier periodo pasado sin procesos nocturnos y con una cifra auditable.

core/wms_3pl.py
CMMS / EAM

Confiabilidad de activos

MTTR y MTBF desde órdenes reales cerradas. Weibull con censura para la vida de cada componente y Crow-AMSAA para saber si un equipo se está deteriorando.

core/confiabilidad.py · analitica/weibull.py
CMMS / EAM

Predicción de fallas

Se entrena con el pasado y se califica con lo que ocurrió después, nunca con una partición al azar. Si el modelo no supera a la tasa histórica (índice de Brier ≤ 0), la pantalla lo dice y no muestra sus probabilidades.

core/analitica/predictivo.py
TarifaX

Comparativo contra SICETAC

Cruza las tarifas negociadas con cada cliente contra el costo de referencia del Ministerio de Transporte por ruta y configuración vehicular. Las tarifas por kilo o por caja se informan como no comparables.

core/tarifax_comparativo.py
Gestión

Flujos de trabajo configurables

Estados y transiciones son datos: cambiar cómo trabaja un equipo es configurar, no desplegar. Las reglas de una transición son claves registradas en el código, nunca expresiones guardadas en la base.

Dispositivos e integraciones

Cubicador de bajo costo

Estación fija con un ESP32, tres láseres y una báscula que mide largo, ancho, alto y peso de cajas y unidades, y envía la medición al módulo WMS · Cubicaje. Cada cubicador tiene su propio token revocable.

medida = escala × (base − lectura)

Precisión objetivo ±1–2 mm por eje y ±5 g hasta 30 kg, con piezas por menos de US$ 250. Firmware y montaje en hardware/cubicador.

Celular como escáner

Un celular puede escanear códigos y enviarlos al PC donde se registra el movimiento. La sesión de escaneo se guarda en la base de datos compartida, de modo que funciona aunque la API corra en varios procesos.

En Control de Estibas también se puede leer con lector de código de barras o con la cámara del equipo.

SAP

Adaptador para registrar movimientos de mercancía en SAP: mapea centro, almacén, material y cantidad a la estructura del documento de material.

infrastructure/integrations/sap

Importación desde Excel

Los módulos de mantenimiento, lubricación, calidad y tarifas cargan datos maestros e históricos desde plantillas Excel, validadas fila por fila antes de guardar.

Organización del portal

  • Tres paneles. Un panel de espacios de trabajo a la izquierda, la navegación del módulo activo y el área de contenido. Solo aparecen los espacios que la empresa tiene contratados y el perfil permite.
  • Command Center. Tableros transversales para quien tiene módulos de operación; el ingreso lleva al primer espacio permitido.
  • Carga a demanda. Cada pantalla se carga con React.lazy cuando se abre por primera vez.
  • Cliente de API único. src/api/client.ts agrega el token y la cabecera de inactividad a cada llamada.
  • Identidad visual en un solo lugar. src/config/marca.ts: escala de grises de la marca y un único acento para lo interactivo. Los colores de estado (éxito, alerta, peligro) son del dato, no de la marca.

Si Redis se cae

Nadie puede entrar ni seguir trabajando: la API responde 503 a propósito, porque una sesión que no se puede comprobar no se da por buena. La solución es levantar Redis: docker compose … up -d redis.

SECRET_KEY

Debe tener al menos 32 caracteres y no empezar por change-me-in-production; de lo contrario el backend no arranca. Cambiarla cierra todas las sesiones.

Guías detalladas: deploy/SEGURIDAD_SESIONES.md, deploy/actualizar.sh, deploy/nginx-proxy.conf.template.

Convenciones

  • Cambios con especificación. Las funcionalidades nuevas se proponen en openspec/changes antes de implementarse y se archivan al terminar.
  • Seguro por defecto. No hace falta agregar autenticación a una ruta nueva: ya la tiene. Lo que sí hay que hacer es declarar su prefijo en core/modulos.py si pertenece a un módulo nuevo.
  • Lógica compartida en core. Si dos pantallas calculan lo mismo, la fórmula va en un solo módulo de app/core.
  • Comentarios que explican el porqué. El código documenta las decisiones y los errores que se corrigieron, para que nadie los repita.
  • Pull requests desde el fork. Se trabaja en una rama, se abre el PR hacia main y la fusión dispara la validación.
